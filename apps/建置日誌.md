# apps/ 建置日誌（GH200 叢集，FP64 GEMM 應用程式）

目的：建置可在 GPU 上執行、FP64 GEMM 密集的科學應用程式，供 LD_PRELOAD mantissa-zeroing shim 使用。
節點：只用 work1/work2/work3（本次 work1 被其他 job 佔用，實際使用 work2、work3）。

目錄：
- `apps/q-e/`            Quantum ESPRESSO（git submodule，tag `qe-7.6`）
- `apps/qe-inputs/`       QE 測試輸入（ausurf112、si216、si512、pseudo/）
- `apps/gpu4pyscf/`       gpu4pyscf（git submodule，tag `v1.8.1`，原地編譯）
- `apps/pyscf-venv/`      Python 3.12 venv（pyscf 2.14.0、cupy-cuda13x 14.2.0 ...）
- `apps/slurm/`           sbatch 腳本
- `apps/logs/`            Slurm 輸出

## 1. Quantum ESPRESSO 7.6（GPU，NVHPC 26.5 / CUDA 13.2）

### 取得原始碼
```bash
cd /nfs/home/koying/mantissa-optimize
git submodule add --depth 1 https://gitlab.com/QEF/q-e.git apps/q-e
git -C apps/q-e fetch --depth 1 origin tag qe-7.6 && git -C apps/q-e checkout qe-7.6
git -C apps/q-e submodule update --init --depth 1 external/devxlib external/fox external/mbd
```
（外部 submodule 在 head 上先抓好，compute node 其實也有網路。）

### 編譯（`apps/slurm/qe_build.sbatch`，work2，約 1.5 分鐘 `make -j72 pw`）
```bash
module load nvhpc/26.5
./configure CC=nvc F90=nvfortran F77=nvfortran MPIF90=mpif90 \
  --with-cuda=/software/nvhpc/Linux_aarch64/26.5/cuda/13.2 --with-cuda-cc=90 --with-cuda-runtime=13.2 \
  --enable-openmp --with-scalapack=no BLAS_LIBS="-lblas" LAPACK_LIBS="-llapack"
make -j 72 pw
```
- 一次成功，無需修改。DFLAGS = `-D__PGI -D__CUDA -D__FFTW -D__MPI -D__MPI_MODULE`
- CUDA_LIBS = `-cudalib=cufft,cublas,cusolver,curand`（nvfortran 預設為**動態**連結）
- `-lblas`/`-llapack` 在 NVHPC 中實際解析為 NVPL（`libnvpl_blas_lp64_gomp.so.0`）

### 連結檢查
- `ldd bin/pw.x | grep cublas` → `libcublas.so.13`、`libcublasLt.so.13`（math_libs/lib64），以及 NVHPC 的 Fortran 包裝層 `libcufcublas.so`。**動態連結 OK。**
- **重要**：pw.x 本身不直接 import `cublasZgemm_v2`，而是 import NVHPC CUDA-Fortran 包裝函式
  `__pgi_dev_cublaszgemm_hpm`、`__pgi_dev_cublasdgemm_hpm` 等（見下）；這些位於
  `compilers/lib/libcufcublas.so`，它再經由 PLT 呼叫 `cublasZgemm_v2`/`cublasDgemm_v2`/...
  → 因為是跨 .so 的動態呼叫，LD_PRELOAD 攔截 `cublasZgemm_v2`、`cublasDgemm_v2` 仍然有效。
- `libcusolver.so.12` 也 NEEDED `libcublas.so.13`，cuSOLVER 內部的 GEMM 若經由匯出符號呼叫也會被 shim 攔到（需 shim 實測確認）。

pw.x 匯入的 cuBLAS 相關符號（`nm -D --undefined-only pw.x | grep -i cublas`）：
```
__pgi_dev_cublas{d,z}gemm_hpm  __pgi_dev_cublas{d,z}gemv_hpm  __pgi_dev_cublasdtrsm_hpm
__pgi_dev_cublas{d,z}axpy/scal/copy/swap/dot(c)  __pgi_dev_cublasdger_hpm  __pgi_dev_cublaszgerc_hpm
__pgi_cublasGetHandle  cublas_assign_ptr2_cublashandles_
```
libcufcublas.so 匯入的真正 cuBLAS 符號（shim 要包的）：
`cublasDgemm_v2 cublasZgemm_v2 cublas{D,Z}gemmBatched cublas{D,Z}gemmStridedBatched cublas{D,Z}gemv_v2 cublas{D,Z}trsm_v2 ...`

CPU BLAS（NVPL，符號帶版本）：`dgemm_@libnvpl_blas_lp64_gomp.so.0 zgemm_ dgemv_ zgemv_ dsyrk_ zherk_ dtrsm_ ztrsm_ ztrmm_`
（shim 若提供無版本的 `dgemm_`，glibc 會接受它滿足帶版本的參照；若 shim 自己用 version script，則要注意版本名稱。）

### 測試輸入
- `qe-inputs/si216/si216.in`：Si 216 原子鑽石結構（3×3×3，隨機位移 ±0.05 Å，seed 12345），SG15 ONCV NC 贗勢，ecutwfc 30 Ry，**Gamma-only**（實數波函數 → 走 DGEMM）。
- `qe-inputs/si512/si512.in`：同上 4×4×4 = 512 原子，nbnd 1100。
- `qe-inputs/ausurf112/ausurf.in`：QEF 官方 benchmark AUSURF112（Au 112 原子，USPP，k 點 2×2×1 → 複數 → ZGEMM），原檔 `electron_maxstep=2`。
- `qe-inputs/ausurf112/ausurf_conv.in`：同上但 `electron_maxstep=100, conv_thr=1e-8`，跑到收斂。
- 贗勢：`qe-inputs/pseudo/Si_ONCV_PBE-1.2.upf`（quantum-simulation.org SG15）、`Si.pbe-n-rrkjus_psl.1.0.0.UPF`（備用）、`ausurf112/Au.pbe-nd-van.UPF`（QEF benchmarks repo）。

### 執行（`apps/slurm/qe_run.sbatch`）

|---|---|---|---|---|---|
| si216 | work2 | 20（收斂） | -1702.06849116 | 6.07 s | 302 W / 468 W |
| ausurf.in（2 步 benchmark） | work3 | 2（未收斂，by design） | -11408.39041357（第 2 步） | 12.83 s | 369 W / 630 W |

### nsys 分析（`apps/slurm/qe_nsys.sbatch`，`nsys profile -t cuda,cublas,openacc`；統計用 `apps/slurm/kern_frac.py`）
| 輸入 | GPU kernel 總時間 | GEMM kernel 時間 | GEMM / GPU kernel | GEMM / wall |
|---|---|---|---|---|
| si512（Gamma，DGEMM） | 26.95 s | 10.54 s | 39% | 30% |
| si1000（Gamma，DGEMM） | 148.1 s | 77.0 s | 52% | 46% |
| ausurf_conv（k 點，ZGEMM） | 43.45 s | 16.65 s | 38% | 21% |
- 其餘主要是 cuFFT（regular_fft/vector_fft）、cuSOLVER 的 `sytrd4_gpu`（Davidson 子空間對角化）、QE 自己的 OpenACC kernel。
- GEMM kernel 全是 `sm90_xmma_gemm_f64f64_*`（DGEMM）或 `sm90_xmma_gemm_cf64cf64_*`（ZGEMM）。
- nsys 的 cuBLAS trace 只顯示內部的 `cublasLtDDDMatmul` / `cublasLtZZZMatmul`（si1000：27.3 萬次；ausurf：12.5 萬次 ZZZ + 7.8 千次 DDD）。

### 以 cuBLAS API log 確認 QE 實際呼叫的 cuBLAS 函式
`CUBLAS_LOGINFO_DBG=1 CUBLAS_LOGDEST_DBG=stdout mpirun -x CUBLAS_LOGINFO_DBG -x CUBLAS_LOGDEST_DBG pw.x ...`
- si216（Gamma）：`cublasDgemm_v2` 29780 次、`cublasDgemm_v2_64` 4268、`cublasDsyr2k_v2_64` 2611、`cublasDtrsm_v2_64` 505、`cublasDger_v2` 400、`cublasDsyrk_v2` 109
- ausurf.in（k 點，2 步）：`cublasZgemm_v2` 19880、`cublasZgemm_v2_64` 3728、`cublasZher2k_v2_64` 2753、`cublasZtrsm_v2_64` 390、`cublasZherk_v2` 144、`cublasDgemm_v2` 678、`cublasDgemm_v2_64` 288
- **`*_v2_64`（ILP64 版）是 cuSOLVER（libcusolver.so.12）內部呼叫的**；`nm -D --undefined-only libcusolver.so.12` 顯示它經 PLT import
  `cublasDgemm_v2_64 cublasZgemm_v2_64 cublasDsyr2k_v2_64 cublasZher2k_v2_64 cublasDtrsm_v2_64 cublasZtrsm_v2_64 cublas{D,Z}gemmStridedBatched_64 ...`
  → **shim 若只包 `cublasDgemm_v2`/`cublasZgemm_v2`，會漏掉對角化（cuSOLVER）裡的 GEMM；需決定要不要也包 `_64` 版本**（對角化的精度可能比 H·ψ 的 GEMM 更敏感，建議分開開關）。
- 另外 log 顯示 cuBLAS 13.4 啟動時會查詢 `cublasGetFixedPointEmulationMantissaControl / MantissaBitOffset / MaxMantissaBitCount`：CUDA 13 的 cuBLAS 內建 FP64 fixed-point（Ozaki 類）emulation，可控制 mantissa 位元數，或許可作為 shim 以外的對照組。

遇到的問題與修正：
1. **libxc（CUDA）編譯失敗**：`math_functions.h(639): error: expected a "{"`（`rsqrt(double) noexcept(true)`）。原因：libxc 設 `CMAKE_CUDA_STANDARD 98` → `-std=c++03`，但 glibc 2.43 + CUDA 13.2 標頭需要 C++11 以上。
   修正：在 `gpu4pyscf/lib/CMakeLists.txt` 的 libxc ExternalProject 加一行 PATCH_COMMAND：
   `COMMAND sed -i "s/set(CMAKE_CUDA_STANDARD 98)/set(CMAKE_CUDA_STANDARD 17)/" CMakeLists.txt`（這是對 gpu4pyscf submodule 的唯一原始碼修改）
2. **Fortran（SMD solvent）**：`nvfortran-Error-Unknown switch: -std=legacy` → nvhpc module 把 `FC` 設成 nvfortran；改 `FC=gfortran`。
3. **CUTLASS 3.4 + GCC 15**：`matrix.h: error: ... has no member named 'set_slice3x3' [-Wtemplate-body]` → `-DCMAKE_CUDA_FLAGS=-Xcompiler=-Wno-template-body`。
4. cuda arch 只編 `90-real`（CUDA 13 已不支援 sm_70）。

### 重要：cupy 14 沒有 cuTENSOR
- `cupy_backends.cuda.libs.cutensor` 在 cupy 14 已不存在 → gpu4pyscf 的 `contract()` 一律退回 `cupy.einsum`（→ cuBLAS GemmEx）。對 shim 來說是好事（所有張量縮併都經 cuBLAS），代價是多了大量 `cupy_copy`（轉置）kernel 與記憶體暫存。
- sbatch 預設 `CONTRACT_ENGINE=cupy`（等同現況，也可消掉 warning）。
- DF-MP2 的 j3c batch 大小是以 cuTENSOR 的記憶體用量估算（可用記憶體 × 0.8），在 einsum 路徑下會 OOM（Taxol、Raffinose 都 OOM）。
  修正（不改函式庫）：`pyscf-inputs/mp2_test.py` 把 `dfmp2_addons.estimate_j3c_batch` 的 `prefactor` 降到 0.3（環境變數 `MP2_MEM_PREFACTOR`）。

### BLAS 符號（shim 需要攔的名稱）
GPU（cupy → `libcublas.so.13`，由 `module load nvhpc/26.5` 的 LD_LIBRARY_PATH 找到 math_libs/lib64）：
- 以 `CUBLAS_LOGINFO_DBG=1` 實測：cupy 的 float64/complex128 `@`、`dot`、`einsum`、`matmul` **全部走 `cublasGemmEx`**（Atype=`CUDA_R_64F` 或 `CUDA_C_64F`，computeType=`CUBLAS_COMPUTE_64F`），batched matmul 走 **`cublasGemmStridedBatchedEx`**。**不是** `cublasDgemm_v2`！
- cupy 的 `cublas.cpython-312-aarch64-linux-gnu.so` 也 import（帶版本 `@libcublas.so.13`）：`cublasDgemmBatched cublasDgemmStridedBatched cublasDgemv_v2 cublasDsyrk_v2 cublasDtrsm_v2 cublasDgeam cublasDdgmm` 與 Z 版本等（cupy.linalg / cupyx 用）。
- gpu4pyscf 自己的 `lib*.so` 不直接 import 任何 cuBLAS 符號；它的 CUTLASS `grouped_gemm/grouped_dot`（numint.py 多 GPU/group 路徑）在單 GPU RKS 能量計算中 nsys 未觀察到。
- cuSOLVER（`cupy.linalg.eigh` → `sytrd4_gpu`）內部也會呼叫 `cublas*_64`（見 QE 段）。
- 注意：這些 import 帶符號版本 `@libcublas.so.13`；shim 若不用 version script（無版本定義），glibc 會接受；若 shim 用 version script，版本節點需叫 `libcublas.so.13`。

CPU（PySCF 本身，CPU 模式或 gpu4pyscf 中留在 CPU 的部分）：
- `pyscf/lib/libnp_helper.so`、`libcvhf.so`、`libao2mo.so` 等 import **`dgemm_` / `zgemm_`**（無前綴），由 pyscf wheel 內附的 `pyscf/lib/libopenblas-r0-8966572e.3.3.so` 提供。
- numpy 2.5（`numpy.libs/libscipy_openblas64_-f552eb69.so`，ILP64）：`numpy/_core/_multiarray_umath` import **`scipy_cblas_dgemm64_` / `scipy_cblas_zgemm64_`**（CBLAS 介面、帶前綴與 64 後綴）。
- scipy 1.18（`scipy.libs/libscipy_openblas-b7e2810b.so`，LP64）：`scipy/linalg/_fblas` import **`scipy_dgemm_` / `scipy_zgemm_`**。

## 3. 第三個應用：CP2K（NGC 容器，評估後不建議作為 cuBLAS shim 目標）

- 自行編譯 CP2K（toolchain：DBCSR、libint、libxc、ELPA、COSMA...）成本高，改用 NVIDIA NGC 容器 `nvcr.io/hpc/cp2k:v2024.3`（有 arm64 版）。
```bash
sbatch apps/slurm/cp2k_pull.sbatch     # apptainer pull → apps/cp2k/cp2k_v2024.3.sif（8.8 GB，約 5 分鐘）
sbatch --export=ALL,INP=RI-MP2_ammonia,NP=1,HOSTFFT=1 apps/slurm/cp2k_run.sbatch
```
- 容器內 binary：`/opt/cp2k/exe/local_cuda/cp2k.psmp`（CUDA 12.5、`-arch sm_80`，在 H100 上 JIT）；cuBLAS 動態連結 `libcublas.so.12`；import `cublasDgemm_v2 cublasZgemm_v2 cublasSgemm_v2 cublasCgemm_v2`；CPU BLAS 為 NVPL `dgemm_ zgemm_`，另有 `pdgemm_`（ScaLAPACK）。
- **問題**：容器內建 cuFFT 11（CUDA 12.5）在本機（driver 615.71.09、64K page kernel）`cufftPlanMany` 回 `CUFFT_INTERNAL_ERROR`。
  修正：把主機 NVHPC 的 CUDA 12.9 cuFFT 放前面：`apps/cp2k/hostlibs/libcufft.so.11 -> /software/nvhpc/Linux_aarch64/26.5/math_libs/12.9/lib64/libcufft.so.11`，
  執行時 `-B /software` 並 `LD_LIBRARY_PATH=apps/cp2k/hostlibs:$LD_LIBRARY_PATH`（sbatch 參數 `HOSTFFT=1`）。
- 結果 QS_single_node/RI-MP2_ammonia（1 rank × 72 threads）：SCF 10 步，Total FORCE_EVAL energy **-139.427103385610** Ha，wall 81 s。
- **但 GPU 幾乎沒在做 GEMM**：GPU 平均只有 138 W、util 16%；nsys：GPU kernel 16.1 s 中 cuBLAS GEMM 只佔 0.1%，其餘是 DBCSR 的 `smm_acc_*`（自寫 CUDA small-matrix kernel，**不經 cuBLAS**）與 `grid_integrate_density`。大部分時間在 CPU（DBCSR/libxsmm JIT 小矩陣乘，也無法用 dgemm_ 攔截）。
- 結論：CP2K 對 cuBLAS LD_PRELOAD shim 不是好目標，不再投入。

## 4. 給 shim 的重點整理
| 應用 | 需攔截的 GPU 符號 | CPU 符號 |
|---|---|---|

`configs/make.gh200` 重點：`CXX=nvcc`（所有 .C 以 `--x cu -dc` 編成 CUDA），`-O3 -use_fast_math -std=c++20 --expt-extended-lambda -arch=sm_90 -ccbin g++`、

`openmp=no`、`FC=gfortran`（quadpack 等 Fortran 檔，`-fallow-argument-mismatch -std=legacy`）、`LINKER=g++`，
連結 `-lRAJA -lcamp -lcudart -lcuda -lcudadevrt -lnvidia-ml`、NVHPC 的 `-llapack -lblas`（實際為 NVPL）、HPC-X `-lmpi`、`-lgfortran`。

遇到的問題與解法：
1. RAJA v2025.12.2：`External CUB not found` → CUDA 13 的 CUB 在 `$CUDA/include/cccl`，加 `-DCUB_DIR=$CUDA/include/cccl`。
2. RAJA v2025.12.2 的 `MemUtils_CUDA.hpp` 用舊版 `cudaMemAdvise(ptr, n, advice, int device)`，CUDA 13 已改成 `cudaMemLocation` → 編譯失敗。改用 **RAJA v2026.07.1**（已支援 `CUDART_VERSION >= 13000`），它要求 **C++20** → RAJA 與 SW4 都改 `-std=c++20`。
3. SW4 上游設定檔以 `-DCAMP_USE_PLATFORM_DEFAULT_STREAM=1` 讓 RAJA kernel 跑在預設 stream（SW4 用 `cudaStreamSynchronize(0)` 同步）；新版 camp 禁止手動定義（`#error ... ODR violations`）→ 改在 RAJA 的 CMake 設 `-DCAMP_USE_PLATFORM_DEFAULT_STREAM=On`，SW4 端拿掉該 -D。
4. 連結缺 `camp::throw_re` → 加 `-lcamp`。
5. `-DUSE_NVTX` 不開（CUDA 13 沒有 `libnvToolsExt.so`）；NVML 用 CUDA stubs 的 `libnvidia-ml.so` 連結、執行時載入驅動的 `libnvidia-ml.so.1`。
6. 目前 work13 的 `nvidia-smi power.limit` 顯示 **900 W**（本次未改任何功耗設定）。

### nsys kernel 時間佔比（loh1grad-h100，GPU kernel 合計 6.92 s）
| kernel（lambda 所在函式） | 時間佔比 | 每點 DRAM 最少讀/寫（double） | 其中材料陣列 |
|---|---|---|---|
| `rhs4th3fortsgstr_ci`（`src/rhs4th3fortc.C:1088`，內點 lambda + 邊界 lambda），每步 2 次 | 49.7% + 3.6% = **53.3%** | 讀 u×3、mu、lambda；寫 lu×3 = 8 | mu、lambda = **2/8 = 25%** |
| `EW::addsgd4_ci`（supergrid 阻尼，`src/addsgdc.C:43`） | 26.1% | 讀 up、u、um ×3、rho；寫 up×3 = 13 | rho = 1/13 = 7.7% |
| `predfort_ci`（`rhs4th3fortc.C:2409`） | 5.5% | 讀 u、um、lu、fo ×3、rho；寫 up×3 = 16 | rho = 6.3% |
| `corrfort_ci`（`rhs4th3fortc.C:2454`） | 4.8% | 讀 up、lu、fo ×3、rho；寫 up×3 = 13 | rho = 7.7% |
| `vset_to_zero_async` | 4.4% | 寫 3（×2） | 0 |
| `dpdmtfort_ci` | 4.2% | 讀 up、u、um ×3；寫 3 = 12 | 0 |
- **材料陣列佔 DRAM 流量**：每步每點最少約 76 個 double 的讀寫中，材料（mu、lambda 各 2 次、rho 3 次）佔 7 個 ≈ **9%**；以 kernel 時間加權約 **16%**（0.533×25% + 0.261×7.7% + 0.055×6.3% + 0.048×7.7%）。
- 但主 kernel `rhs4th3fortsgstr_ci` **不受 HBM 頻寬限制**：h=100 每次 2.50 ms、最少 ~1.0 GB → 有效僅約 0.4 TB/s；它受 L1/暫存器載入與 FP64 管線限制
  （13 點樣板，每個 mu/lambda 值被鄰點重複載入約 13 次）。所以材料位元真正的去處是**晶片內資料路徑與 FP64 乘法器**，而不是 HBM：
  - 二階導數項：`mux1 = mu(i-1)*strx(i-1) - tf*(mu(i)*strx(i) + mu(i-2)*strx(i-2))`（`rhs4th3fortc.C:1248` 起），內部 strx=1，所以 mux 是截斷值的小整數係數線性組合（只多 2–3 位有效位），再乘 `(u(i±1,2) - u(i))` → 乘法器一個運算元是低位全零的係數。
  - 混合導數項：`la(i-2,j,k) * (u2(i-2,j-2,k) - u2(i-2,j+2,k) + 8*(...))`（`rhs4th3fortc.C:1358` 起，每分量 116 ops）→ **原始儲存的 la/mu 直接當乘數**。
  - supergrid 阻尼：`rho(i+1,j,k) * dcx(i+1) * (...)`（`addsgdc.C:135` 起）→ rho 直接進乘法器；predictor/corrector 是 `dt2 / rho[i]`（除法，`rhs4th3fortc.C:2444`、`2469`）。
  - 與 N 體不同，SW4 的係數在乘法之前只經過同量級值的加減（不經過 sqrt/倒數），尾數零位能保留到乘法器。

### 截斷插入點（已實作，環境變數控制）
- 共用 header：`apps/sw4/src/MantTrunc.h`（`manttrunc::from_env()`、`apply()`、`apply_array()`）。
  `MANT_BITS=<k>`（0–51；未設定、空字串或 ≥52 → 完全不動作）、`MANT_ROUND=trunc|nearest`（預設 trunc）；對 double 的 uint64 表示，nearest 先加 `1<<(52-k-1)`，再清掉低 52−k 位；NaN/Inf 不動。
- **插入點 1**：`apps/sw4/src/setupRun.C:375–394`，`EW::setupRun()` 中 `set_materials()`（`setupRun.C:373`）之後 → 截斷 mRho、mMu、mLambda（各向異性時為 mRho、mC）。
  此時材料剛由 `convert_material_to_mulambda()`（mu=rho·vs²、lambda=rho·vp²−2mu）算好、MPI 重疊區也已同步，而 dt、supergrid、衰減、MR 係數、震源（依 mu 縮放）都還沒算
  → 截斷等同「換成一個相對誤差 ≤2^-k 的材料模型」，之後所有衍生量都一致。在 host 上以 managed memory 做一次（h=50 的 3.8 億個值使 start up 由 7.33 s 增為 7.55 s）。
- **插入點 2**（只在有 `attenuation` 時）：`setupRun.C:427–443`，`setup_viscoelastic()` 之後 → 因為它會把 mMu/mLambda 改寫成 unrelaxed 模數、並算出 mMuVE/mLambdaVE（又回到完整尾數），所以對 mMu、mLambda、mMuVE[a]、mLambdaVE[a] 再截一次。
- 輔助函式 `mant_trunc_sarrays()`（`setupRun.C:111` 起）：截斷、`MPI_Allreduce` 統計、rank 0 印一行
  `[MANT] SW4 <arrays>: MANT_BITS=36 MANT_ROUND=trunc, <總數> values, <被改到的數目> changed`。
- 原生對照 binary `optimize/sw4_native`：用 `git show HEAD:src/setupRun.C`（`apps/sw4-tpl/native/setupRun.C`）重新編 setupRun 並連結（`apps/sw4-tpl/native/native.mk`），其他 object 完全相同。

### MANT_BITS 驗證（`sw4_compare.py`：接收站時間序列逐點最大相對差，0 = 逐位相同）
| 比較 | 輸入 | [MANT] 被改到的值 | 最大相對差 |
|---|---|---|---|
| `sw4`（MANT_BITS 未設定）vs `sw4_native`（原始 setupRun.C） | loh1gradf-h50（1971 vs 1972） | — | **0（逐位相同）** |
| 同上（重建含衰減 hook 的版本後） | loh1gradf-h100（1980 vs 1981）、loh3-h100（1982 vs 1983） | — | **0（逐位相同）** |
| 36 位 trunc | loh1gradf-h50（1973） | 372,247,425 / 378,835,875（98.3%） | 5.4e-11 |
| 36 位 nearest | loh1gradf-h50（1974） | 同上 | 3.4e-11 |
| 20 位 trunc | loh1gradf-h50（1975） | 373,711,525 / 378,835,875 | 3.8e-6 |
| 36 位 trunc | loh1grad-h50（整數梯度，1953） | 188,868,900（49.9%） | 1.3e-10 |
| 36 位 nearest | loh1grad-h50（1954） | 同上 | 1.6e-11 |
| 36 位 trunc | loh1-h50（原版整數區塊，1957） | **732,050（0.19%）** | 3.9e-12 |
| 36 位 trunc | loh3-h100（衰減，1984） | 插入點 1：**405** / 100,875,375；插入點 2：**269,001,000 / 269,001,000** | 1.2e-10 |
| 重建後 36 位 trunc vs 重建前 | loh1gradf-h50（1985 vs 1973） | 同上 | **0（逐位相同）** |
- 36 位截斷使材料相對擾動 ≤ 2^-36 ≈ 1.5e-11，接收站輸出擾動 3–5e-11；對照離散誤差：同一輸入 h=100 與 h=50 的接收站峰值振幅相差 4–10%（例如 sta01 max|ux| 28.48 vs 29.64），截斷影響小 9 個數量級；20 位（2^-20 ≈ 1e-6 → 輸出 4e-6）也小 4 個數量級。步數（dt）與 solver phase 時間完全不變。
- **材料本身的有效位數**：原版 LOH.1 的區塊材料（vp=6000、vs=3464、rho=2700 → mu=rho·vs²、lambda 都是整數）本來就少於 36 位，截斷幾乎改不到任何值（0.19%，只有 z=999–1001 的介面區塊）；
  整數梯度（0.1、0.064 × 50 m 的深度）也有一半的值本來就是短尾數。**做功耗實驗必須用 `loh1gradf`（非整數梯度，98% 的值被改到）或真實 3D 模型**，否則原生與截斷版的位元內容幾乎一樣。
- 衰減模型：`setup_viscoelastic()` 會用 Q 值與鬆弛頻率重算 mu/lambda 並產生 mMuVE/mLambdaVE，就算原始區塊材料只有幾位有效數字，時間迴圈實際用的陣列仍是完整尾數（插入點 2 改到 100%）。
- 衰減版的 start up 在 host 上逐點做 dgels（`openmp=no`），32M 點約 3 分鐘；solver 只有 4 s（62 步），**不適合當功耗實驗輸入**，只用來驗證插入點 2。

## 6. MFEM（CUDA 後端，Partial Assembly 擴散算子 + CG）

### 版本與原始碼

遇到的問題與解法：
1. `make BUILD_DIR=... cuda -j72`：`libmfem.a` 已經產生，但之後的 `deprecation-warnings` 子 make 在原始碼目錄執行、找不到設定（`MFEM is not configured`）而回傳錯誤。改成「`make BUILD_DIR=... config ...` + `make -C <builddir> lib`」兩步驟就正常。
2. **n=128（2.10M 個元素）執行時 `illegal memory access`**：幾何因子 `J` 的大小 = 9·Q1D³·NE = 9·125·2,097,152 = 2.36e9 > 2³¹，MFEM 的 `Vector`/kernel 索引是 32 位元 `int` → 溢位。單 GPU 上限約 NE < 1.9M（n ≤ 123）。代表性輸入改用 **n=112**（J = 1.58e9，安全）。
3. `nvidia-smi` 顯示 GPU `power.limit` = **900 W**（不是 1000 W；本次沒有改任何功耗設定）。
4. `-mass`（加 MassIntegrator）時，在 p=3 曲面網格上 Mass 的求積是 Q1D=8，沒有 (4,8) 的特化 kernel → 走通用 fallback，每次 CG 迭代從 1.9 ms 變 13.8 ms。**功耗實驗請用預設的純擴散**；Mass 只用來驗證截斷 hook 能動。

### Driver：`apps/mfem-bench/ex1_bench.cpp`（改寫自 examples/ex1.cpp，未動 MFEM 的 examples）
- 問題：3D 擴散 `-div(κ∇u) = f`，單位立方體，齊次 Dirichlet；製造解 `u = sin(πx)sin(πy)sin(πz)`，`κ = 1 + 0.5(x+y+z)`（`-ck` 改成常數 1）。
- 網格：`MakeCartesian3D(n,n,n)` 六面體 → `SetCurvature(p)` → 內部節點擾動 `a·sin(πx)sin(πy)sin(πz)`（a=0.05，三個分量係數不同，邊界面上為 0，區域仍是單位立方體）。
  **這很重要**：若用未擾動的直角網格 + 常數係數，pa_data 的 3 個非對角分量全是 0、對角分量在各元素間重複，截斷幾乎沒東西可截；擾動網格 + 變係數才會讓 pa_data 每個值都是滿 52 位尾數（像真實應用的曲面網格）。
- κ 與 f 用 p 階節點內插的 `GridFunctionCoefficient`（在 GPU 上由 QuadratureInterpolator 求值；κ 在物理座標上是線性，對等參網格是精確表示）。避免 host 端數千萬次 `FunctionCoefficient` 求值 → n=112 的 setup 只要 8.3 s。
- 求解：`-d cuda`、PA、`OperatorJacobiSmoother` 前處理的 `CGSolver`（rtol 1e-10），`-rep R` 重複從 X=0 解 R 次；`-fixed N` 固定 N 次迭代；`-matvec M` 另外單獨計時 M 次 A·x。
- 印出（%.17g）：`(B, A·B)`、`||A·B||`、每次求解的迭代數/最終殘差、`||X||`、`(X,B)`、節點上對製造解的 max/RMS 誤差、時間與 GDOF/s。

### 遇到的問題與解法
1. **GPU 功耗上限顯示 900 W**：work11 上 `nvidia-smi --query-gpu=power.limit` = 900 W（GPU 本身的 limit；模組層 nv_power 為 1000 W）。未更動（依規定不動 nv_power）。
2. **KOKKOS GPU 版本身不能逐位重現**：`NBinKokkos::bin_atoms()`（`src/KOKKOS/nbin_kokkos.cpp:161`）用 `atomic_fetch_add` 把原子放進 bin → 鄰居表順序每次不同 → 力的加總順序不同。同一支原版執行檔連跑兩次：
   - LJ 第 0 步壓力最後一位就不同（`-5.019669344282853` vs `…854`），6000 步後溫度差 2e-4（混沌放大，統計上等價）。
   - EAM 第 0 步 thermo 16 位全同，但逐原子力已有 ~1e-15 的差，數百步後 thermo 在 1e-15 相對量級分岔。
   → 「未設定 MANT_BITS 與原生逐位相同」無法用重跑直接證明；改用 **原生 vs 原生 的雜訊底線** 當對照（見驗證）。

### 流量佔比估計
**LJ**：ρ*=0.8442、鄰居半徑 2.8σ → full list 每原子 77.6 個鄰居，截斷內 55.3 對。
- 每原子每步 DRAM ≈ 鄰居索引 77.6×4 B + x_i 24 B + f_i 24 B + type/numneigh/ilist ~12 B ≈ **370 B**（x_j gather 大多命中 L1/L2）。
- 係數：`m_params` 在 constant/參數空間 → DRAM **0%**；運算元層面每對 ~18 個 FP 運算中只有 1 個乘法（lj1·r6inv）用到係數，而 bench 的 lj1=48 本來就只有 1 個尾數位元 → **可截空間 = 0**。

**EAM**：n=4/3.615³=0.0847 Å⁻³，鄰居半徑 5.95 Å → 74.7 鄰居，截斷 4.95 Å 內 43.0 對。
- DRAM：係數表 84 KB，整個常駐 L1/L2（每 SM L1 256 KB、L2 50 MB）；每次 kernel 的強制載入上限 ≈ 84 KB×132 SM ≈ 11 MB，對比每次 kernel 的 DRAM 流量 ≈ 16.4M×~350 B ≈ 5.7 GB → **係數佔 DRAM 流量 ≈ 0.2%**。每原子每步 DRAM ≈ 2×(鄰居索引 299 B) + x/f/rho/fp ~110 B ≈ 710 B，幾乎全是鄰居表與原子資料。
- L1→暫存器（load 位元組）：Kernel AB 每對讀 rhor 4 個係數（32 B）→ 每原子 1.43 KB 係數 vs 2.13 KB 其他（鄰居索引 + x_j 24 B×74.7）→ **~40%**；Kernel C 每對讀 rhor 3（+3）+ z2r 4 個係數 → 2.4–3.4 KB vs 2.5 KB → **~50–58%**。
- 乘法器運算元：Kernel C 每對約 25 個乘法中約 6 個有一個運算元是係數（c0·p 兩次、rdr·c3/c4/c5、c3·p）→ ~25% 的乘法、~12% 的乘法器輸入位元；Horner 第一個 FMA 之後中間值就是全尾數（與 N 體「計算深度」效應相同）。
- 結論：EAM 的係數確實「直接進乘法器」，但只在 L1 以內流動、佔 DRAM 流量 ≈ 0；LJ 基準則完全沒有可截位元。**預期兩者在功耗上都看不到明顯效益 → 適合當負面對照**。

**建議先做 MFEM 的功耗上限實驗**，理由：
1. 係數（pa_data）佔 DRAM 流量約 43%、PA kernel 佔 GPU 時間 65.7%，而且是串流讀取後直接當 FP64 乘數 —— 同時命中已量到有效的兩條路徑（記憶體 copy/triad：450 W 快 14–17%；純 FP64 乘加：省 138 W）。先前自寫 CG 只截矩陣值（≤1.7%）的問題（索引與向量佔多數流量）在 PA 裡不存在：PA 沒有稀疏索引、係數本身就是主要流量。
2. 三者中功耗最高（641 W、100% util），上限壓到 450–600 W 就會進入功耗限制區；GPU reduction 可逐位重現，原生 vs 截斷的差異容易判讀。
3. 建議比較 原生 / 36 位 nearest / 20 位 nearest（20 位 nearest 誤差仍只有 1e-9；trunc 有系統性偏差），`-n 112 -o 3 -rep 4`（要更長就加 `-rep`）。

第二順位 **SW4**：係數佔 DRAM 流量較低（≈9%），效益若有，主要來自晶片內資料路徑與乘法器（mu/la 被 13 點樣板重複載入），可檢驗「非 HBM 受限的 stencil」會不會省；
功耗只有約 500 W，上限要壓到約 300–450 W；務必用 `loh1gradf`（非整數梯度），原版 LOH.1 的材料本身只有幾位有效數字，截斷幾乎改不到值。
**LAMMPS 當負面對照**（係數幾乎不走 DRAM、EAM 有「計算深度」效應、LJ bench 無可截位元），若要測建議 EAM、上限 450–550 W，預期 0–1%。

共通注意：三個應用在同一輸入重跑時都看到 1.5–5% 的功耗漂移（溫度與先後順序），ΔW 必須用 ABBA 並從冷卻狀態開始。
